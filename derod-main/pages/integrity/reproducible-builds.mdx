# Reproducible Builds

A released binary is only as trustworthy as its link to the source it claims to come from. That
link is checkable: DERO's build is deterministic, and the published binaries rebuild
**byte-for-byte** from the public source tree today.

## Result

Release113 — `3.5.2-113.DEROHE.STARGATE+01102022`, published 1 October 2022 — reproduces exactly on
six of seven platform targets. `linux/amd64`, `windows/amd64`, `darwin/amd64`, `darwin/arm64`,
`linux/arm64` and `linux/arm7` are byte-identical to the released files; `freebsd/amd64` was built
natively with cgo and does not reproduce on Linux
([why](#how-the-build-achieves-determinism)).

The darwin release ships as a universal binary. Both of its slices rebuild exactly, and reassembling
them behind a standard `lipo`-style wrapper reproduces the published file whole
(`5c9f9620b6519f30bd1bc5288ab24cf9dea3baeafc6d32bf83d58564ebe6efb8`) — the wrapper is a header plus
alignment padding and carries no content of its own.

Applying the same method to `derod-linux-amd64` across the surrounding releases:

| Release | Published | Result |
|---|---|---|
| Release110 | 2022-09-28 | No — built without `-trimpath` |
| **Release113** | **2022-10-01** | **Byte-identical** |
| Release114 | 2022-10-27 | Byte-identical |
| Release116 | 2023-02-19 | Byte-identical |
| Release117 | 2023-03-19 | Byte-identical |
| Release140 | 2023-06-17 | Byte-identical |
| Release142 | 2025-08-13 | No — native cgo build |

The numbering is a build counter, not a release count — the repository carries 65 tags, of which 63
are numbered `ReleaseNNN` spanning 2 to 142 (the other two are `Release4a` and `DeroHE`). Twelve
gaps run through the history, 117→140 being the largest. Missing numbers like 111 and 112 were
simply never published.

Both exceptions track recorded build settings rather than any known difference in code. Release110
predates `-trimpath`, so it embeds the original builder's absolute source paths; rebuilding without
`-trimpath` closes the gap to about 10 KB, and the remainder is consistent with those paths being
unknown to anyone but the original builder. Release142 was compiled natively with cgo, so its output
depends on the host C toolchain — every recorded Go build setting matches and 212 bytes differ.
Neither is claimed as reproduced: both are releases whose build cannot be reconstructed from a
different machine.

### When determinism landed

`build_package.sh` gained `-trimpath` and `-ldflags=-buildid=` — the two changes that make output
deterministic — in **Release113**, and is byte-identical between Release113 and Release114.
Release110 has neither, which is precisely why it is the one that does not reproduce.

The `Release114` note reads *"Reproducible builds implemented."* What Release114 actually adds is
the Go [VCS stamp](#reproducing-releases-that-carry-a-vcs-stamp) — build provenance metadata, not
the determinism, which was already shipping. Release113 was the current release from 1 to 27
October 2022.

## Reproduce it yourself

Runs on an ordinary Linux machine. No node, no chain data, no trust in this page.

**1. Source, pinned to the signed tag**

```sh
curl -sL -o Release113.tar.gz \
  https://github.com/deroproject/derohe/archive/refs/tags/Release113.tar.gz
sha256sum Release113.tar.gz
# c9467cfb795f6cf982f295d41bec120af5e074dd925e180171f0fcffc9f326c4
tar xzf Release113.tar.gz && cd derohe-Release113
```

**2. Toolchain** — not a guess. It is recorded in the released binary, readable with
`go version -m`, along with every setting needed below:

```
derod-linux-amd64: go1.19.1
    build  -trimpath=true
    build  CGO_ENABLED=0
    build  GOARCH=amd64
    build  GOOS=linux
    build  GOAMD64=v1
```

```sh
curl -sLO https://go.dev/dl/go1.19.1.linux-amd64.tar.gz
sha256sum go1.19.1.linux-amd64.tar.gz
# acc512fbab4f716a8f97a8b3fbaa9ddd39606a28be6c2515ef7c6c6311acffde
tar xzf go1.19.1.linux-amd64.tar.gz && export PATH=$PWD/go/bin:$PATH
```

**3. Build and compare**

Write the binary **outside** the source tree — step 4 hashes the tree, and anything left behind in
it will change the answer.

```sh
GOOS=linux GOARCH=amd64 CGO_ENABLED=0 GOAMD64=v1 \
  go build -trimpath -ldflags=-buildid= -o /tmp/derod ./cmd/derod
sha256sum /tmp/derod
# 1fc5a7a4bcf1130fb1b7b0100b4beec8c53610e48984f279d286e10e366be70c
```

That is the `derod-linux-amd64` shipped in `dero_linux_amd64.tar.gz`
(`f2d22868c4d4a49f7a1792731bf73f9bc3b69ee426f5d04fab1fea1c57efe969`).

No network is needed for this step. `vendor/` is committed in-tree and `go.mod` declares `go 1.17`,
so the toolchain builds in vendor mode: the same hash comes out with `GOPROXY=off` and empty
module and build caches.

**4. Confirm the source is the signed source.** A downloaded tarball proves nothing on its own —
bind it to the project's signed history:

```sh
git init -q . && git add -A && git write-tree
# b604a482f87825e1b11cef621e6eb5f017cda82f
```

Release113 ships no `.gitignore`, so run this on a pristine extraction — `git add -A` will absorb
any build output left in the tree and change the hash. Note also that `git init` makes the
directory a repository, so a *later* rebuild from it will pick up a Go
[VCS stamp](#reproducing-releases-that-carry-a-vcs-stamp) and no longer match.

That tree hash is the exact tree named inside GPG-signed commit
`89a1e1e8bf4cf09d204710e053e7e202a640fc6b`, an ancestor of the live `main` branch.

**5. Optional: check the source against a third party.** Go's module mirror keeps an independent
copy of the first-party tree, and its hash is recorded in a public append-only transparency log —
neither is operated by DERO or by GitHub:

```sh
V=v0.0.0-20221001111649-89a1e1e8bf4c
curl -s "https://proxy.golang.org/github.com/deroproject/derohe/@v/$V.info"
# {"Version":"...","Time":"2022-10-01T11:16:49Z","Origin":{"VCS":"git",
#  "URL":"https://github.com/deroproject/derohe",
#  "Hash":"89a1e1e8bf4cf09d204710e053e7e202a640fc6b"}}

curl -s "https://sum.golang.org/lookup/github.com/deroproject/derohe@$V"
# 13369518
# github.com/deroproject/derohe v0.0.0-20221001111649-89a1e1e8bf4c
#   h1:NryIz1KtPNOnHPD+tNCT6ZD4W6ieYCciQkmJsiT99xM=
```

The pseudo-version encodes the same commit and the same timestamp. Every one of the 344 first-party
files in that mirrored copy is byte-identical to the GitHub tarball above. This covers the
first-party tree only — `vendor/` is excluded from Go module zips (see [Limits](#limits)).

### Reproducing releases that carry a VCS stamp

From Release114 onward the binaries embed Go's VCS metadata (`vcs.revision`, `vcs.time`,
`vcs.modified`). A tarball build cannot carry that stamp and will never match. Build from a git
checkout at the recorded revision instead:

```sh
git clone https://github.com/deroproject/derohe.git && cd derohe
git checkout 358fab62bdf443a02358c67b322f0685ec072303

# vcs.modified=true means the release was built from a tree with
# uncommitted changes; the stamp records the flag, not the diff
echo "" >> DIRTY

GOOS=linux GOARCH=amd64 CGO_ENABLED=0 GOAMD64=v1 \
  go build -trimpath -ldflags=-buildid= -o /tmp/derod ./cmd/derod
# 847ea80b83a1df887d245085db60a9b0626aacb6cd4f0f192eb2e982643c5529
```

**That `vcs.modified=true` deserves a direct answer**, because it says the shipped binary was built
from a tree carrying changes that were never committed anywhere public. The rebuild settles what
those changes could have been. Starting from the clean commit and dirtying only an untracked
placeholder — enough to flip the flag, and touching no compiled code — produces a binary that is
byte-identical to the released one. Since the output is a deterministic function of the code that
goes in, identical output means the original build's uncommitted changes did not reach any compiled
Go package. The same holds for Release116, Release117 and Release140, which match by the same
method.

Release113 carries no VCS stamp, which is why the tarball method works for it. It is also the
release with no self-reported build provenance at all — and the one the
[tree-hash binding](#reproduce-it-yourself) above covers instead. That binding is the stronger of
the two: a stamp is a claim the builder writes about itself, while a tree hash is a cryptographic
statement about the source that anyone can recompute.

## How the build achieves determinism

Go binaries embed no build timestamp, and `build_package.sh` supplies the rest: `-trimpath` strips
absolute source paths, `-ldflags=-buildid=` strips the build ID, `GOOS`/`GOARCH` cross-compilation
means the build host's OS and hardware do not reach the output, and `vendor/` is committed in-tree
so the dependency code cannot drift between builds. The usual reasons a binary is called
irreproducible — timestamps, host OS, hardware, dependency versions — do not apply, and the build
needs no network at all.

**The one host-dependent variable is cgo**, and reading `CGO_ENABLED` out of the Release113
binaries shows a distinctive pattern: `0` for `linux/amd64`, `windows/amd64`, `linux/arm64` and
`linux/arm7` — and `1` for `freebsd/amd64` alone.

Go enables cgo by default for a **native** build and disables it when **cross-compiling**. Exactly
one target carries cgo, and it is FreeBSD. The simplest explanation consistent with that is a
FreeBSD build host: `GOOS=freebsd` was native and picked cgo up automatically, while every other
target was a cross-compile and did not. It is not the only possible one — a deliberately configured
cross C toolchain could produce the same result — but it is the only one that follows from
`build_package.sh` as written, which never sets `CGO_ENABLED` or `CC`.

That accounts for three things at once — why the script never needed to set `CGO_ENABLED` (Go's
defaults already produced this pattern), why `freebsd/amd64` alone will not reproduce on Linux, and
why the other six reproduce from any host. The linkage is real rather than a stray flag: the
FreeBSD binary is dynamically linked against `libc.so.7` and `libthr.so.3` while every other target
is static. It was also not required — the same target builds cleanly with `CGO_ENABLED=0`, so
nothing in DERO depends on cgo.

**A practical consequence:** because the script leaves `CGO_ENABLED` at Go's default, its output
depends on where it runs — six of the seven targets reproduce from a Linux host, and `freebsd/amd64`
does not. Whether it reproduces on a FreeBSD host has not been tested here. The script is not
deficient; it is correct on the machine it was written for. Set `CGO_ENABLED` explicitly to the
value recorded in the released binary, as above. **A mismatch produced this way is not evidence of
tampering** — it is a different build configuration.

## What this establishes

**It establishes nothing about the behaviour of that source.** Start here, because it is the part
most easily lost: reproducibility is a supply-chain property. It links an artifact to its inputs
and says nothing about whether those inputs are correct. A reproducible build of flawed code is
still flawed code, reproducibly. What the code *does* is answered by reading and testing it — see
[Network Consensus](/integrity/network-consensus-validation) and
[Verify the Supply](/integrity/verify-the-supply).

**What it does establish: the binary is the source.** For every platform except FreeBSD, the
program DERO published in October 2022 is a faithful compile of the published, GPG-signed source
tree. There is no room in those binaries for code absent from the repository — which means the
published source is the whole of what there is to review, and a claim about DERO's behaviour has to
be made against code anyone can read rather than against a binary nobody can inspect.

That is a narrow result, and it is worth being plain about how narrow. It does not say the source
is sound, that the network is safe, or that any particular dispute about DERO is settled. It says
one thing: for these releases, the question "does the shipped binary match the shipped source?" has
a checkable answer, and the answer is yes.

## Limits

**Host-dependent builds cannot be reproduced elsewhere.** `freebsd/amd64` on Release113 and all of
Release142 were compiled natively with cgo, so their output depends on the build machine's C
toolchain. This is a property of native cgo builds generally; in both cases every recorded Go
setting matches, with the difference confined to C-linked code.

**Vendored dependencies are unpinned.** Of the 4,907 files in the source tree, 252 are first-party
Go files and 4,563 are third-party code under `vendor/`. That vendored code is compiled into the
binary, but nothing pins it to upstream: `go.mod` is three lines with no `require` directives, there
is no `go.sum`, and there is no top-level `vendor/modules.txt` — so no recorded versions and no
hashes to check against. This does not weaken the reproducibility result, which is exactly why the
build is hermetic. It does bound what "the binary is the source" covers: the third-party portion of
that source is verifiable only by reading it, not by comparing it to a published dependency.

**Provenance of the published binaries rests on GitHub.** The release manifests are PGP-signed, but
the signing key carries no third-party certification and is the same key that signs the project's
commits — so the manifest and the [commit binding](#reproduce-it-yourself) share one trust root
rather than corroborating each other. What distinguishes the commit is that GitHub reports it as
`verified`, binding that key to the account. The same account uploaded both binaries and manifest,
so the signature is not independent evidence of when the files appeared.

Two server-side facts do bound that. GitHub's asset `created_at` (`2022-10-01T11:25Z` for
Release113) is set by GitHub, not the uploader; and release asset IDs are a monotonic counter, so
Release113's assets (`79628755`–`79628795`) sit between Release110's and Release114's, where a later
re-upload could not. The *source* has independent cover — the Go module mirror and checksum
transparency log in [step 5](#reproduce-it-yourself) — but no third-party mirror of the 2022
*binaries* is known to exist.

One smaller note for anyone repeating this: the `Release113` git tag is lightweight — unsigned and
mutable — so cite the commit `89a1e1e8`, not the tag.
