# Studio

![Studio](/assets/studio.png)

The **Studio** is Hologram's integrated development environment for creating, deploying, and managing TELA applications. It provides tools for local development, batch deployment, and version control. For testing with real blockchain state, use [Simulator Mode](/simulator).

<Callout type="success">
  **Complete Development Workflow**: Develop locally with hot reload, deploy to blockchain, and manage versions—all from one integrated environment.
</Callout>

## Overview

Studio consists of four main sections:

| Section | Purpose |
|---------|---------|
| **Serve** | Local development server with hot reload |
| **Deploy** | Batch deployment of TELA applications |
| **My Content** | Manage your deployed TELA applications |
| **Actions** | Version control and content management |

## Serve (Local Dev Server)

The Serve tab provides a local development server for testing TELA apps before deployment.

### Starting the Server

1. Navigate to **Studio > Serve**
2. Click **"Choose Directory"**
3. Select a folder containing your TELA app (must have `index.html`)
4. Server starts automatically on the first available port (scans the 50080-51000 range to avoid DERO service ports)

### Features

| Feature | Description |
|---------|-------------|
| **Hot Reload** | Automatic browser refresh on file changes |
| **telaHost API** | Full [telaHost API](/telahost-api) available during development |
| **CORS Support** | Proper headers for local development |
| **MIME Types** | Correct content types for all web files |
| **Cache Busting** | Fresh content on every reload |

### Supported File Types

- **Web files**: `.html`, `.htm`, `.css`, `.js`, `.mjs`, `.json`
- **Images**: `.svg`, `.png`, `.jpg`, `.jpeg`, `.gif`, `.webp`, `.ico`
- **Fonts**: `.woff`, `.woff2`, `.ttf`

### Hot Reload Behavior

- File changes detected automatically (300ms debounce)
- Only reloads when Browser tab is viewing local content
- Recent changes displayed in Studio tab
- XSWD connection maintained during reload

### API Reference

```go
StartLocalDevServer(directory string) -> {
    success: true,
    url: "http://127.0.0.1:50080",
    port: 50080
}

StopLocalDevServer() -> { success: true }

GetLocalDevServerStatus() -> {
    running: true,
    url: "http://127.0.0.1:50080",
    port: 50080,
    directory: "/path/to/app",
    watcherActive: true
}
```

## Deploy

The Deploy tab provides tools for deploying both complete TELA applications and raw DVM-BASIC smart contracts to the blockchain.

### Upload Smart Contract (Raw SC)

For developers building standalone smart contracts or testing backend logic, Hologram provides a direct SC deployment interface:

1. **Select "Upload SC"** — Toggle to the raw smart contract deployment mode
2. **Paste Code** — Paste your DVM-BASIC smart contract code into the editor
3. **Deploy** — Hologram automatically estimates gas and deploys the contract

<Callout type="info">
  **Simulator Safe**: When deploying raw smart contracts in Simulator Mode, Hologram uses a specialized connect/disconnect pattern that temporarily pauses the Gnomon indexer to prevent the simulator daemon from crashing due to its single-WebSocket limitation.
</Callout>

### Batch Deployment Process (TELA Apps)

1. **Choose Directory** — Select your app folder
2. **Configure** — Review or adjust the auto-filled name, description, dURL, icon, content type, compression, and MODs
3. **Review** — Inspect the file list, preflight summary, and any oversized-file warnings
4. **Deploy** — Watch progress as files are uploaded

### Configuration Options

| Option | Description |
|--------|-------------|
| **Application Name** | Display name for your app |
| **Description** | Brief description (shown in Discover) |
| **dURL** | Optional memorable URL (e.g., `myapp.tela`) |
| **Icon URL** | Optional icon (HTTPS, HTTP, SCID, or IPFS) |
| **Content Type** | Updateable (Ring 2) or Immutable (Ring > 2) |
| **Compression** | Optional GZIP compression before deployment |
| **MODs** | Optional smart contract functionality |

When available, Hologram now auto-infers metadata from:

- `package.json` — `displayName`, `name`, `description`, `icon`
- `index.html` — `<title>`, `<meta name="description">`, `<link rel="icon">`
- `README.md` / `README.txt` — first markdown heading as a description fallback

If a name is inferred, Hologram also auto-generates a default dURL slug such as `my-app.tela`.

### Icon URL Validation

Hologram validates icon URLs in real-time as you type:

- **HTTPS URLs** — Validated for proper format
- **HTTP URLs** — Accepted with warning (HTTPS recommended)
- **SCID** — 64-character hex string (on-chain image reference)
- **IPFS** — `ipfs://` protocol URLs

Visual feedback indicators:
- ✓ Green checkmark for valid HTTPS/SCID/IPFS
- ⚠ Yellow warning for HTTP URLs
- ✗ Red X for invalid formats

### dURL Tag Detection

Hologram automatically detects special dURL suffixes and shows contextual descriptions:

| Suffix | Description |
|--------|-------------|
| `.tela.lib` | Library — A collection of reusable DOCs that can be embedded in other apps |
| `.tela.shard` | DocShard — A shard DOC (part of a larger file split across multiple contracts) |
| `.tela.shards` | DocShards — An INDEX containing DocShards that require reconstruction |
| `.tela.bootstrap` | Bootstrap — A collection of TELA apps/content for bootstrapping |

When you enter a dURL with one of these suffixes, Hologram displays a badge with the appropriate description. If the selected folder appears to contain shard output, Hologram also warns if the dURL does not end with `.tela.shards`.

### MODs (Modification Operations)

MODs add smart contract functionality to your INDEX. MODs require Ring 2 (updateable content).

#### Variable Store MOD

Select **one** Variable Store MOD to add on-chain key-value storage:

- `vs1`, `vs2`, etc. — Different variable store implementations
- Single selection only — Choose the storage system that fits your needs
- Automatically enforces Ring 2 — MODs require updateable content

#### Transfer MODs

Select **multiple** Transfer MODs to enable different transfer capabilities:

- `tx1`, `tx2`, etc. — Various transfer and deposit functionalities
- Multiple selection — Combine different transfer types
- Automatically enforces Ring 2 — MODs require updateable content

#### MOD Picker Modal

When you enable MODs, a modal opens with:

- **Variable Store section** — Select one storage system
- **Transfer section** — Select multiple transfer types
- **Selected MODs summary** — Shows combined tags (e.g., `vs1,tx1,tx2`)
- **Clear all** — Reset selections

The selected MOD tags are included in the INDEX contract's `mods` field.

### Library Installation Flow

When installing a library (dURL ending in `.tela.lib`), Hologram provides an **"Embed in INDEX"** workflow:

1. **View library contents** — See all DOCs in the library
2. **Click "Embed in INDEX"** — Adds library DOC references to your INDEX
3. **Automatic DOC reference addition** — Library DOCs are automatically included in your INDEX's `DOC1`, `DOC2`, etc. variables

This makes it easy to reuse library components across multiple TELA apps.

### Deployment Confirmation Modal

For mainnet deployments, Hologram shows a confirmation modal with enhanced safety:

{/* removed: "Password required" bullet — the deploy confirmation modal has no wallet-password field as of 2026-06-12 (no password input in Studio.svelte; the wallet is already unlocked); restore if built */}

- **Acknowledgement checkbox** — Must confirm you understand this deployment is permanent and will consume real DERO
- **Gas estimate display** — Shows estimated gas cost before deployment
- **Network indicator** — Clearly shows "Mainnet" or "Simulator"

<Callout type="warning">
  Mainnet deployments are permanent and cost real DERO. Always test in Simulator Mode first.
</Callout>

### Content Types

| Type | Ring Size | Description |
|------|-----------|-------------|
| **Updateable** | 2 | Owner can update the INDEX contract |
| **Immutable** | > 2 | Content is permanently fixed |

<Callout type="info">
  Updateable content allows you to push updates to your app. Immutable content provides stronger guarantees that the app won't change.
</Callout>

### File Processing

During deployment, Hologram:

1. **Scans directory** — Finds all supported files and detects DOC types
2. **Infers metadata** — Reads `package.json`, `index.html`, and `README` when present
3. **Builds a preflight summary** — Shows source files, expected DOC contract count, and oversized-file warnings
4. **Optionally compresses files** — Applies GZIP only when the user enables compression
5. **Deploys DOCs** — Each file becomes a TELA-DOC-1 contract
6. **Creates INDEX** — Links all DOCs together
7. **Registers dURL** — If specified

### File Size Limits

| Limit | Value |
|-------|-------|
| Max file size | 18KB (TELA specification) |
| Compression | Optional GZIP toggle before deployment |
| Preflight summary | Shows `Source Files -> DOC Contracts + 1 INDEX` before deploy |
| DocShards | Use Studio > DocShards when a file still exceeds the limit |

    durl: "myapp.tela",
    deployedDocs: [
        { name: "index.html", scid: "..." },
        { name: "styles.css", scid: "..." },
        ...
    ],
    message: "Successfully deployed 2 DOCs and created INDEX"
}
```

|--------|-------------|

| **SCID** | Smart contract ID (click to copy) |

### Quick Actions

Each app in your content list has quick action buttons:

| Action | Description |
|--------|-------------|
| **View** | Open the app in Browser |
| **Update** | Deploy a new version (Ring 2 only) |
| **Clone** | Download current files to local directory |

- **Total Views** — Combined view count across all apps

## Actions (Version Control)

The Actions tab provides Git-like version control for TELA applications. Every update to an INDEX creates a new "commit" that can be viewed, compared, or reverted to.

<Callout type="success">
  **Blockchain-Native Version Control**: Unlike traditional version control, TELA commits are immutable and permanently stored on-chain. Every version of your app is preserved forever.
</Callout>

### Version History Modal

Click the **Version History** button (clock icon) in the Browser toolbar or use **Actions > View History** to open the Version History modal for any TELA app.

#### Timeline View

The left panel shows a chronological timeline of all commits:

| Element | Description |
|---------|-------------|
| **Version number** | v1, v2, v3... (deployment order) |
| **Semantic label** | Describes what changed (e.g., "Updated styles.css, app.js") |
| **Block height** | When this version was deployed |
| **TXID** | Transaction hash (click to view in Explorer) |
| **Current badge** | Green badge on the latest version |

#### Semantic Labels

Hologram automatically generates descriptive labels by analyzing file changes between versions:

| Label Example | Meaning |
|---------------|---------|
| "Initial deployment" | First version (v1) |
| "Updated index.html" | Single file modified |
| "Updated styles.css, app.js" | Multiple files modified |
| "Added favicon.svg" | New file added |
| "Removed old-script.js" | File removed |
| "Updated 5 files" | Many files changed (truncated) |

<Callout type="info">
  Semantic labels are generated by comparing consecutive versions. For the last 5 commits, Hologram fetches actual file content to determine what changed.
</Callout>

#### Detail View

Click any version to see its details in the right panel:

- **Block height** — When deployed
- **Transaction ID** — Full TXID (click to copy)
- **dURL** — Registered URL at this version
- **File count** — Number of files in this version
- **File browser** — Tabs to view each file's content
- **DOC SCIDs** — List of DOC contract IDs

### Compare Mode

Toggle **Compare Versions** to diff two versions:

1. Click **Compare Versions** button
2. Select first version (older)
3. Select second version (newer)
4. View file-by-file diff

#### File Diff Display

The diff view shows changes organized by file:

| Status | Color | Meaning |
|--------|-------|---------|
| **Added** | Green | File exists in newer version only |
| **Removed** | Red | File exists in older version only |
| **Modified** | Yellow | File changed between versions |

For modified files, Hologram shows line-by-line changes:
- Lines with `-` prefix (red) — Removed content
- Lines with `+` prefix (green) — Added content

Use the **Clone** button in the Version History modal or Actions tab to download files.

        "app.js": "console.log..."
    },

// Compare two commits
DiffCommits(scid string, fromCommit int, toCommit int) -> {
    success: true,
    fromCommit: 1,
    toCommit: 2,
    fileDiffs: [
        {
            fileName: "styles.css",
            status: "modified",
            lineDiffs: [
                { line: 5, type: "modified", oldContent: "color: red;", newContent: "color: blue;" }
            ]
        },
        {

            status: "added",
            lineDiffs: []

    summary: "1 file modified, 1 file added",

```

### Performance Notes

- **TXID Caching** — Transaction IDs are cached after first retrieval to speed up subsequent history loads
- **Semantic Labels** — Only generated for the last 5 commits to balance detail vs. performance
- **Content Fetching** — File content is loaded on-demand when you select a commit

## DocShards

When a file exceeds TELA's 18KB size limit, you can split it into multiple DOC contracts called **shards**.

### How DocShards Work

1. **File is split** — Large file divided into sequential chunks that fit in DOCs
2. **Shards deployed** — Each chunk becomes a separate TELA-DOC contract
3. **Shard INDEX created** — A special INDEX (dURL ending in `.tela.shards`) links all chunks in order
4. **Automatic reconstruction** — When loading the app, Hologram concatenates all shards back into the original file

### Using the DocShard Manager

Hologram's **Studio > DocShards** tool now supports both picker-based and drag-and-drop workflows:

- **Shard File** — Drop any file to split it into DOC-sized shards
- **Reconstruct** — Drop a shard folder to rebuild the original file
- **Compression toggle** — Optionally compress the file before sharding
- **Result card** — Shows shard count, compression mode, and the actual output location

Shard output is written next to the source file on your filesystem, not into a hidden app directory.

### Creating DocShards

```go
// Split a file into shard-sized chunks
ShardFile(filePath string, compress bool) -> {
    success: true,
    shardCount: 2,
    outputDir: "/path/to/source/folder",
    compressed: true,
    message: "File sharded into 2 parts"
}

// Reconstruct a file from local shard files
ConstructFromShards(shardPath string) -> {
    success: true,
    outputPath: "/path/to/reconstructed/file",
    size: 28672,
    message: "File reconstructed successfully"
}
```

### dURL Conventions

| Suffix | Description |
|--------|-------------|
| `.tela.shards` | A shard INDEX containing references to shard DOCs |
| `.tela.shard` | An individual shard DOC (part of a larger file) |
| `.tela.lib` | A library of reusable DOCs |
| `.tela.bootstrap` | A collection of TELA apps/content for bootstrapping |

<Callout type="info">
  DocShards are transparent to the end user when the INDEX uses a `.tela.shards` dURL. Use them when compression alone isn't enough to fit under the 18KB limit.
</Callout>

## Workflow Examples

### New App Development

1. **Create project directory**
   ```
   mkdir my-tela-app
   cd my-tela-app
   ```

2. **Create files**
   ```html
   <!-- index.html -->
   <!DOCTYPE html>
   <html>
   <head>
     <link rel="stylesheet" href="styles.css">
   </head>
   <body>
     <h1>My TELA App</h1>
     <script src="app.js"></script>
   </body>
   </html>
   ```

3. **Start local dev server**
   - Studio > Serve > Choose Directory

4. **Develop with hot reload**
   - Edit files, see changes instantly

5. **Deploy when ready**
   - Studio > Deploy > Choose Directory > Deploy

### Updating Existing App

1. **Clone current version**
   - Actions > Clone > Enter SCID

2. **Make changes locally**
   - Edit files in cloned directory

3. **Test with local dev server**
   - Serve > Choose cloned directory

4. **Deploy update**
   - Deploy > Choose directory
   - Use same dURL as before

<Callout type="warning">
  Updates only work for Updateable content (Ring 2). Immutable content cannot be changed.
</Callout>

## Best Practices

1. **Test locally first** — Use Serve before deploying
2. **Use meaningful names** — Help users find your app
3. **Write good descriptions** — Shown in Discover tab
4. **Choose dURL carefully** — Can't be changed after deployment
5. **Consider immutability** — For apps that should never change
6. **Check file sizes** — Keep under 18KB per file
7. **Avoid `*/` in code** — Breaks TELA's comment wrapper

## Troubleshooting

| Issue | Cause | Solution |
|-------|-------|----------|
| Hot reload not working | File type not watched | Check supported file types |
| Deployment fails | File too large | Enable compression or use shards |
| "Expecting declaration" error | Code contains `*/` | Use `'*' + '/'` instead |
| dURL not resolving | Gnomon not synced | Wait for indexing to complete |
